# ADR-0001:编译优先执行模型

- 状态:已接受
- 日期:2026-07-04
- 关联铁律:#1、#3
- 关联规则:ARCH-010、ARCH-011、ARCH-012

## 背景

深度学习框架存在 eager 逐算子解释与图静态编译两条路线。本项目后端矩阵中
Intel NPU(OpenVINO)与昇腾(CANN 图模式)本质是图编译设备,逐算子下发性能
不可接受甚至不可行;跨算子融合、AOT 内存规划与编译产物缓存也只能在整图视角
完成。需要把铁律 #1① 固化为对全体贡献者可判定的执行模型规则。

## 决策

编译路径是唯一默认执行路径:构图 → verify → pass 管线 → `Backend::compile()`
产出 `Executable` → 缓存 → 重复执行。eager 仅作逃生舱,准入限定为三类(ARCH-011):

1. 用户显式开启 debug/eager 开关(API 上有明确开关参数);
2. 编译路径对某算子/dtype 组合不支持时的自动回退(必须打 WARN 级英文日志,
   内容含算子名与回退原因);
3. 单算子的单元测试。

禁止增加「图 + eager 混合执行」的第三种模式,需要时另立 ADR(ARCH-012)。
判定方法:eager 落点收敛为 `Backend::launch` 调用点白名单(登记于
docs/architecture/execution-model.md ARCH-011);白名单外新增调用点即打回。

## 备选方案

- eager 优先 + 事后 JIT(PyTorch 1.x 路线):优点是调试直观、上手快;缺点是
  NPU 类后端逐算子下发性能不可行,整图融合与内存规划机会丢失。否决:与铁律 #1①
  和后端矩阵(铁律 #3)直接冲突。
- 编译 / eager 双模式同权并列:优点是使用灵活;缺点是行为边界不可判定,测试矩阵
  与维护成本翻倍。否决:「同权」必然导致 eager 蔓延,违背编译优先。

## 后果

- 正面:整图融合与 AOT 内存规划成为可能;编译产物可缓存以摊销编译成本;
  各后端接入口径统一为 `compile()` 产出 `Executable`。
- 负面:首次执行含编译延迟;调试体验依赖 IR 文本 dump(`--dump-ir-after`)。
- 跟进:docs/architecture/execution-model.md 固化 ARCH-010/011/012 与 eager
  回退链;全部示例、文档、测试的主路径使用编译执行(ARCH-010)。
