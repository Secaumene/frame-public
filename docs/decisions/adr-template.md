# ADR 模板

> **强制等级**:规范(MUST)
> **相关铁律**:按各 ADR 决策内容标注(本模板适用于全部铁律相关决策)
> **面向读者**:实现代码的工程师
> **最后更新**:2026-07-04

## 1. 命名与篇幅规则

【ADR-001】【MUST】ADR 全文 ≤ 60 行;超长说明决策粒度过大,应拆分为多个 ADR。判定方法:对每个 ADR 文件执行 `wc -l docs/decisions/NNNN-*.md`,结果 ≤ 60。

【ADR-002】【MUST】ADR 文件名匹配正则 `^[0-9]{4}-[a-z0-9]+(-[a-z0-9]+)*\.md$`(四位编号 + 英文小写连字符标题);编号 = 现有最大编号 + 1;正文中文。判定方法:scripts/check_language_policy.py 的文件名检查 + review 时核对编号连续性。

## 2. 模板全文(新建 ADR 时整体复制)

```markdown
# ADR-NNNN:<中文标题>

- 状态:提议 | 已接受 | 推迟(重评条件:<可判定条件>) | 已废弃 | 被 ADR-MMMM 取代
- 日期:YYYY-MM-DD
- 关联铁律:#N
- 关联规则:如 CPP-010

## 背景
<为什么需要决策,2-5 句>

## 决策
<选定方案,一句话结论 + 要点列表 + 判定方法>

## 备选方案
<每个备选:方案名 / 优点 / 缺点 / 否决原因,各 1-2 句>

## 后果
<正面影响 / 负面影响与代价 / 需要跟进的动作(文档、代码、CI)>
```

## 3. 写作要求

- 不确定的第三方 API、版本号、行为,必须写「【待查证】<问题> —— 来源:<官方文档名>」,禁止凭记忆编造(与 BE-000 同款格式)。
- 「决策」一节必须含可机械执行的判定方法(grep 命令、CI 检查名、文件存在性检查等);禁止「尽量」「优雅」「合理」等不可判定措辞。
- 跟进动作若落为代码桩,使用统一 TODO 格式:`TODO(FRAME-{IMPL|DESIGN|TEST|DOC|PERF|DEP}): 说明。参考:<路径>。完成判据:<可判定条件>`。
- 状态为「推迟」的 ADR 必须写明可判定的重评条件;推迟期间实现代码不得绑定任一候选方案。
